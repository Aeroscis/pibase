## 1. `pi::` 家族包的提升 [P3]（开放）

现在每个成员是**自己的包**：`find_package(pibase)` 给 `pi::base`，
`find_package(piplugin)` 给 `pi::plugin`。命名空间 `pi::` 在 CMake 意义上是家族层，
但家族层本身**还没有一个包**。

可选做法：让某个包（或一个新的伞包）以 `find_package(pi COMPONENTS base plugin)`
的形式统一提供，成员作为 component。需要跨仓库协调每个成员的安装与导出规则，
所以先记下来，等家族成员数量真的让"逐个 find_package"变成负担时再做。

## 2. `PI_APP_RESULT_BASE` 的取值是否需要更强约束 [P3]（开放）

现在约定"app / 成员库的自定义错误码取 `<= -100`"，`PI_APP_RESULT_BASE` 是起点。
若将来出现两个互不相关的消费者各自编号并共用一个成员库，可能需要更明确的分段
（例如按使用者分配区间），或干脆改为"自定义码必须带使用者前缀的符号名"。
目前没有第二个消费者，不做。

## 3. 根层薄度的量化红线要不要自动化 [P4]（开放）

`README.md` 写了一条红线：根层的平台相关代码只能停留在 typedef / 编译器内建的量级。
今天那是 `pi_refcounted_*` 里的两个 interlocked 调用。要不要用脚本把这条红线变成
一个可执行的检查（例如统计 `#if PI_PLATFORM_*` 分支的行数上限），等根层第一次
有人试图加东西时再评估——现在加检查属于为没有的问题写代码。
